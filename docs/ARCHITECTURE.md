# Устройство «Просмотрщика LAS»

Документ описывает слои, контракты между ними и правила, которые нельзя
нарушать при доработке. Зачем приложение устроено именно так — в
[`PLAN.md`](PLAN.md).

## Слои

```text
LasViewer (WinUI 3)             окна, диалоги, сценарии, журнал, обновления
        │
AMK.LasViewer.Engine (C#)       поиск и запуск движка, JSON-RPC, жизненный цикл
        │ stdin/stdout, JSON-RPC 2.0
lasviewer_engine (Python)       данные, расчёты, агент, песочница
```

Технологический профиль: WinUI 3, `net10.0-windows10.0.26100.0`, минимальная
система `10.0.17763.0`, только x64, unpackaged, self-contained Windows App SDK.
Встроенный Python 3.12 (embeddable, x64).

**Данными владеет движок.** Разбор LAS, обработка кривых, проверки качества и
всё, что делает агент, живут в Python. Приложение не разбирает файлы само и не
дублирует формулы: иначе у скрипта агента и у планшета окажутся две разные
версии одних данных.

## Протокол движка

- JSON-RPC 2.0, одно сообщение — одна строка UTF-8 без BOM, `\n` в конце;
- ответы сопоставляются с запросами по `id`, запросы можно слать параллельно;
- сообщение движка без `id` — уведомление (прогресс, журнал);
- пакетные запросы не поддерживаются;
- имена полей — `snake_case`; на стороне C# это обеспечивает
  `JsonNamingPolicy.SnakeCaseLower`;
- коды ошибок — стандартные JSON-RPC (`-32700`…`-32603`); внутренняя ошибка
  несёт трассировку Python в `error.data.traceback`.

Методы:

| Метод | Назначение |
| --- | --- |
| `system.hello` | Рукопожатие: версии протокола, движка, Python, пакетов |
| `system.ping` | Проверка связи, возвращает переданную строку |
| `system.shutdown` | Штатное завершение: движок отвечает и выходит |

### Правила протокола

1. **stdout принадлежит протоколу.** Движок при старте перенаправляет
   `sys.stdout` в stderr, а ответы пишет в сохранённый двоичный поток. Одна
   строка `print` в stdout сломала бы разбор ответов. Код движка и
   библиотек пишет только в stderr — он уходит в журнал приложения.
2. **Версия протокола сверяется при рукопожатии.** `PROTOCOL_VERSION` в
   `lasviewer_engine/__init__.py` и `EngineHost.SupportedProtocolVersion`
   меняются вместе при любом несовместимом изменении. При расхождении
   приложение отказывается работать с движком: неверно понятый ответ хуже
   отказа.
3. **Неверные параметры и ошибка обработчика различаются.** Привязка
   параметров проверяется до вызова (`-32602`); `TypeError` изнутри
   обработчика — внутренняя ошибка (`-32603`).

## Жизненный цикл движка

`EngineHost` — единственный владелец процесса.

- **Поиск** (`EngineLocator`): в установленном приложении — `python\python.exe`
  и `engine\` рядом с `LasViewer.exe`; из репозитория — Python разработчика и
  исходники `engine\`.
- **Запуск:** встроенный Python запускается с `-I` (изолированный режим: не
  видит пакеты и переменные `PYTHON*` пользователя). Путь к пакету движка задаёт
  `python312._pth` — встроенный Python игнорирует `PYTHONPATH`.
- **Задание Windows:** процесс движка привязывается к объекту задания с флагом
  «завершить при закрытии». Если приложение упадёт, система завершит движок и
  всё, что он породил, — в том числе зависший скрипт агента.
- **Авария:** закрытие канала работающего движка переводит его в состояние
  `Failed` с кодом выхода и последними строками stderr; ожидающие запросы
  завершаются `EngineUnavailableException`, а не висят до тайм-аута.
- **Остановка:** `system.shutdown`, ожидание 3 с, затем принудительное
  завершение дерева процессов. Окно откладывает закрытие до остановки движка.
- **Перезапуск:** `StartAsync` на работающем движке сначала останавливает его.
  Закрытие канала при остановке аварией не считается — поколения процессов
  различаются счётчиком.

События `EngineHost` приходят из фоновых потоков; окно переносит их в свой
`DispatcherQueue`.

## Приложение

| Файл | Ответственность |
| --- | --- |
| `MainWindow.xaml(.cs)` | Разметка, меню, строка состояния движка |
| `Services/AppInfo.cs` | Версия, права процесса, каталоги данных |
| `Services/AppLog.cs` | Журнал: файл на день в `%LOCALAPPDATA%\AMK\LasViewer\logs` |
| `Services/DialogService.cs` | Очередь `ContentDialog` |
| `Services/AutoUpdateService.cs` | Проверка, загрузка, проверка SHA-256, запуск установщика |
| `Services/UpdateFlow.cs` | Сценарий обновления с вопросами пользователю |

Правила, перенесённые из «Визуализации данных»:

- **диалоги показываются только через `DialogService`**: WinUI допускает один
  открытый `ContentDialog`, второй падает исключением из `async void`;
- **тема закреплена светлой**, акцентная палитра задана явно;
- **установщик запускает приложение через `explorer.exe`**: приложение с
  правами администратора теряет системные диалоги выбора файлов.

## Обновления

- канал — только HTTPS (`AutoUpdateService.UpdateRoot`); другая схема
  отвергается при создании службы. Контрольная сумма приходит в том же файле,
  что и имя установщика, и по HTTP ничего бы не защищала;
- `las-viewer-version.txt`: версия, имя установщика, SHA-256 — все три строки
  обязательны;
- `AppId` в `installer/setup.iss` и ключ удаления в `AutoUpdateService`
  совпадают — по нему определяется, какая копия установлена;
- установщик удаляет прежние `engine\` и `python\` целиком перед копированием:
  модуль, убранный из новой версии, не должен остаться от старой.

## Правила внесения изменений

1. Разбор данных и расчёты — только в движке, не в коде окон.
2. Несовместимое изменение протокола — вместе с `PROTOCOL_VERSION`.
3. Новые пакеты движка — через `engine/requirements.txt` с точной версией и
   `scripts/Prepare-Python.ps1`, чтобы у всех пользователей были одинаковые
   библиотеки.
4. Раздельно фиксировать, что подтверждено сборкой, что тестами, а что
   запуском. Успешная сборка не является проверкой работы.
